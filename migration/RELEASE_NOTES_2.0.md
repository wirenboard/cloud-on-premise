# On-Premise 2.0 — что нового

Мажорный релиз: большой синк с актуальным облаком + несовместимые изменения в
учётных записях. Данные пользователей **не удаляются** — они мигрируют на месте.

Краткий список изменений — в [`CHANGELOG.md`](CHANGELOG.md). Здесь — подробности и
порядок обновления. Релиз включает всё из 1.3.0–1.5.0 (отключаемый email,
ребрендинг, security-фикс туннельного авторизатора).

---

## Новые возможности

### Дашборды Grafana по организациям
Новый сервис `clients-grafana` (Grafana 12.2.2) — отдельные пользовательские
дашборды в разрезе организаций. Своё состояние (дашборды, пользователи, организации)
Grafana хранит во встроенной SQLite (`/var/lib/grafana`, том `clientsGrafanaData`),
а метрики читает из TimescaleDB как datasource.

### Метрики на TimescaleDB
Хранилище метрик переведено с InfluxDB на **TimescaleDB**. Приём метрик от
контроллеров теперь выполняет сервис **Telegraf** (HTTPS + mTLS, ограничение частоты
через Traefik). Для одноузловой поставки запускается один инстанс TimescaleDB (без
upstream-HA: Patroni/etcd/HAProxy не используются).

> **Важно:** история метрик за прошлый период в новые графики **не переносится**.
> Существующая база InfluxDB при обновлении сохраняется в бэкап, новые метрики
> копятся в TimescaleDB с нуля. Графики за период до обновления будут пустыми;
> исторические данные при необходимости можно поднять из бэкапа отдельно.

### Вебхуки FRP-туннелей
Отдельный инстанс бэкенда `tunnel-webhooks-backend` для обработки вебхуков
FRP-туннелей (изолирован от основного трафика приложения).

### Отдельная очередь для писем
К уже существовавшим очередям фоновых задач добавился отдельный воркер для
почты — письма больше не ждут за тяжёлыми задачами метрик.

### Веб-сервисы контроллеров через туннели
Веб-интерфейсы сервисов контроллера (например, Node-RED) публикуются на поддоменах
`<серийник>-<порт>.apps.<домен>` — до 20 сервисов на контроллер, доступ только через
облачную авторизацию. Требует wildcard DNS-запись `*.apps.<домен>` и сертификат с
этим доменом: он входит в обязательный набор, который проверяет `make check-certs`
(см. README).

### Быстрые туннели
Пул прогретых каналов до контроллера — страницы за туннелем открываются заметно
быстрее.

### Геолокация сессий
Страна/город в списке активных сессий. Включается `GEOIP_ENABLED=True` в `.env`:
база DB-IP City Lite (~62 МБ) скачивается автоматически при `make run`, дальше
геолокация работает без запросов наружу (см. README, раздел GeoIP).

### Срок хранения метрик
Новая переменная `METRICS_RETENTION_DAYS` (по умолчанию 30 дней) — сколько
хранится история метрик контроллеров.

## Несовместимые изменения

### Вход по email
Email стал логином: **обязателен и уникален** (без учёта регистра). Учётные записи
без email или с логином, не совпадающим с email, больше не допускаются.

Схема новой версии требует этого на уровне базы, но сама учётные записи не исправляет.
Поэтому заполненную базу 1.x нужно привести в порядок **до** миграции — этим занимается
`make upgrade` (см. ниже), данные при этом **не теряются**.

### Адрес регистрации
Старый эндпоинт `/users-sign-up/` удалён (в upstream заменён на
`/users/registrations/`). Встроенный фронтенд обновляется синхронно — страница
регистрации для пользователя продолжает работать.

### `EMAIL_ENABLED` стала обязательной
Стек не стартует без явного `EMAIL_ENABLED=True` или `EMAIL_ENABLED=False` в
`.env`. В 1.x незаданная переменная молча включала email — теперь выбор нужно
сделать явно (иначе письма могли тихо теряться при недонастроенной почте).
`make upgrade` переносит переменную из старого файла как есть. Если её там нет
(`.env` старше 1.5.0 или строку удалили), она останется пустой и обновление
остановится, пока вы не выберете `True` или `False` явно.

### Новые имена почтовых переменных
`EMAIL_URL` больше не собирается: настройки SMTP передаются напрямую под именами
Django — `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`,
`EMAIL_NOTIFICATIONS_FROM` и `EMAIL_USE_TLS` (порт 587) либо `EMAIL_USE_SSL`
(порт 465). Цели `make generate-email-url` больше нет. Старые переменные
(`EMAIL_SERVER`, `EMAIL_LOGIN`, `EMAIL_PASSWORD`, `EMAIL_PROTOCOL`) `make upgrade`
конвертирует в новые имена автоматически.

### `ADMIN_USERNAME` больше не задаётся
Логин — это email, поэтому отдельного имени пользователя нет: администратор
создаётся и входит по `ADMIN_EMAIL`.

## Перед обновлением

Обновляться нужно, **только если** вы сейчас работаете на версии 1.x — версия указана
в файле `VERSION` и в подвале веб-интерфейса. Перед `make upgrade` убедитесь:

- **Сертификат перевыпущен с `*.apps.<домен>`.** Веб-сервисы контроллеров — штатный
  функционал 2.0, поэтому `*.apps.your-domain.com` входит в обязательный набор доменов.
  Если сертификат 1.x его не покрывает, `make upgrade` остановится на проверке
  сертификата ещё до бэкапа: перевыпустите сертификат (см.
  [Сертификаты TLS](README.md#4-сертификаты-tls)) и добавьте DNS-запись `*.apps`.
- **Резервное место есть.** Бэкап (`pg_dump` + `influx backup`) пишется в `./backups` —
  убедитесь, что на диске хватает места под копию базы.
- **Стек 1.x запущен.** Не останавливайте контейнеры перед апгрейдом — `make upgrade`
  сам ими управляет. `migration_doctor` работает внутри живого контейнера бэкенда, а на
  остановленном стеке запускается разово отдельным контейнером — чинить учётки можно и там.
- **У каждого пользователя должен быть корректный, уникальный email, равный логину.**
  Это и есть смысл миграции. Конфликты, которые придётся разрешить вручную:
  - **админ без email** (типичный случай 1.x: `username="admin"`, `email=""`) —
    `MODE=auto` подставит ему `ADMIN_EMAIL`, но возьмёт значение из окружения уже
    работающего контейнера бэкенда: только что вписанное в `.env` он не увидит. Если
    правите `.env` сейчас, пересоздайте контейнер (`make run`) либо задайте адрес
    вручную через `MODE=resolve`;
  - **пользователи без email** — для каждого нужно указать реальный email;
  - **дубли email** (без учёта регистра) — оставить можно только одного владельца,
    остальным назначить другой адрес.
- **Метрики InfluxDB не конвертируются.** Историю копируем рядом по возможности; новые
  метрики копятся в TimescaleDB с нуля. Копия лежит в `./backups/influx-<дата>/`. Если
  обновление напечатало предупреждение, что копия пуста, история осталась только в
  docker-томе `influxData` — не удаляйте его.
- **Сервер выдержит 2.0.** Относительно 1.5.0 добавились TimescaleDB, Telegraf, Grafana,
  отдельные воркеры метрик и почты и второй бэкенд под вебхуки — памяти нужно больше.
  Предполётная проверка контролирует только диск, поэтому сверьтесь с
  [системными требованиями](README.md#минимальные-системные-требования) и
  [производительностью фоновых задач](README.md#производительность-фоновых-задач) заранее.
- **Если конфликтов нет** (у всех уже корректные уникальные email = логин) — миграция
  пройдёт **без единого ручного действия**.

## Как обновиться (1.x → 2.0)

Всё делает одна команда. Цель `upgrade` появилась только в 2.0, на чекауте 1.x её нет:

```bash
git pull
make upgrade
```

Обойти её нельзя: пока установка остаётся на 1.x, `make run`, `make update` и
`make restart` отказываются стартовать и отправляют сюда. Иначе образы 2.0
мигрировали бы базу при старте — без бэкапа и без починки учётных записей.

Она сначала проходит шесть проверок при работающем облаке и **ничего не меняет**,
пока все шесть не пройдены. Запускать можно сколько угодно раз — это и есть
репетиция обновления.

| Проверка | Что делает |
|---|---|
| Конфигурация | Собирает новый `.env` из `.env.example`, перенося значения старого: одноимённые как есть, переименованные под новыми именами, ключи и токены дословно. Прежний файл остаётся рядом как `.env.bak-<дата>`. Обязательные переменные, значение которых вывести нельзя, остаются **пустыми** — впишите их: пустое значение обязательной переменной проверка считает незаданным. Необязательные получают значение из примера. При нескольких запусках копий `.env.bak-*` будет несколько; конфигурация 1.x — в самой старой |
| Переменные окружения | Все обязательные заданы, `EMAIL_ENABLED` имеет распознаваемое значение |
| TLS-сертификат | Покрывает все домены, включая новый `*.apps.<домен>` |
| Место на диске | Не меньше 6 ГБ на разделе с репозиторием: образы 2.0 занимают около 5 ГБ. Если Docker хранит образы на другом разделе (`docker info --format '{{.DockerRootDir}}'`), проверьте место и там |
| Образы | Скачаны заранее — окно простоя не будет ждать реестр. Причину отказа проверка не показывает, смотрите вручную: `VERSION=$(cat VERSION) docker compose pull` |
| Учётные записи | Совместимы со схемой 2.0 (email становится логином) |

**Если проверка учётных записей потребовала правки — сначала снимите дамп.**
`make fix-users` в любом режиме кроме `scan` меняет таблицу пользователей в
работающей базе 1.x, и делает это раньше, чем обновление снимет свой бэкап.
Прежние пары логин/почта нигде не сохраняются, поэтому порядок такой:
`make backup`, потом починка.

Когда всё готово, команда покажет, что произойдёт дальше, и **спросит подтверждение**.
Ответ по умолчанию — «нет», так что случайно уронить облако нельзя. Без терминала
(например, `ssh host 'make upgrade'`) подтверждение задать нельзя — запускайте
`make upgrade CONFIRM=yes`.

После подтверждения начинается простой:

1. **Бэкап** — `pg_dump` основной базы (и копия InfluxDB, если она ещё запущена).
   База InfluxDB **не конвертируется** в TimescaleDB — она сохраняется рядом, чтобы
   при необходимости обратиться к историческим метрикам позже.
2. **Остановка приложения.** Базы остаются подняты — миграции идут в них. Учётные
   записи проверяются ещё раз, когда в базу уже никто не пишет.
3. **Миграции** на образе новой версии.
4. **Запуск.** Заодно облако сразу рассылает контроллерам конфигурацию сбора
   метрик, не дожидаясь получасового цикла.

**Сколько это займёт.** Тяжёлое уже сделано до простоя, поэтому окно — это время
дампа базы плюс миграции: на типичной инсталляции считанные минуты. Контроллеры
переподключаются сами: токены туннелей не меняются, перенастраивать их не нужно.

**Что сказать пользователям.** После обновления вход выполняется по email, а не по
логину. У тех, чей логин не совпадал с почтой, он изменится — предупредите заранее.

**Решите до обновления.** Срок хранения метрик `METRICS_RETENTION_DAYS`
записывается в хранилище в момент его создания, то есть во время обновления.
Позже его можно только уменьшить: чтобы увеличить, хранилище придётся
пересоздать, потеряв историю. Если 30 дней по умолчанию не подходит,
раскомментируйте и задайте переменную до `make upgrade`.

**Уберите остатки 1.x.** Сервисов `influx` и `worker-influx` в 2.0 нет, поэтому
обновление их не останавливает: воркер на старом образе продолжает работать уже
против новой схемы, а InfluxDB занимает память и диск. Когда убедитесь, что 2.0
работает, погасите их:

```bash
VERSION=$(cat VERSION) docker compose up -d --remove-orphans
```

Docker-том `influxData` при этом остаётся на месте — исторические метрики никуда
не деваются. Если включили `GEOIP_ENABLED=True`, скачайте базу: обновление, в
отличие от `make run`, этого не делает — `make update-geoip`.

### Устранение конфликтов пользователей

`migration_doctor` запускается внутри ещё работающего контейнера бэкенда (через
Django ORM, затрагивает только `username`/`email`), идемпотентен — запускайте,
пока не останется 0 конфликтов.

Из режимов ниже базу не меняет только `scan`; `auto`, `resolve` и `dump` начинают с
одних и тех же авто-исправлений.

```bash
# Только посмотреть конфликты — единственный режим, который ничего не меняет:
make fix-users MODE=scan

# Авто-исправления: администратору с пустым email подставляется ADMIN_EMAIL; пустой
# email, чей логин сам является адресом, забирает его; при расхождении побеждает
# email — логин пользователя становится равен адресу. Пустые адреса, из которых
# нечего вывести, и дубли остаются человеку:
make fix-users MODE=auto

# Интерактивный мастер: сначала те же авто-исправления, затем запрос адреса по
# каждому оставшемуся конфликту с проверкой валидности и коллизий:
make fix-users MODE=resolve

# Безголовый режим (без TTY): выгрузить конфликты в файл, отредактировать,
# применить. Выгрузке тоже предшествуют авто-исправления, поэтому в файл попадает
# только то, что требует решения:
make fix-users MODE=dump          # пишет migration/conflicts.yaml
#   ...отредактируйте поле new_email в каждой строке...
make fix-users MODE=apply         # читает файл обратно
```

Когда `make fix-users MODE=scan` сообщает `Conflicts: 0`, повторно запустите
`make upgrade` — миграция пройдёт, образ 2.0 поднимется.

> ⚠️ Не перезапускайте стек 1.x между ремонтом учёток и обновлением: при каждом
> старте 1.x заново создаёт пользователя `admin` с адресом из `ADMIN_EMAIL`, и в
> базе снова появляется дубль. Обновление это заметит и остановится — тогда
> повторите `make fix-users` и дайте пересозданному `admin` любой другой адрес.

### Если что-то пошло не так

Пока подтверждение не дано, миграция не выполнялась и облако работает. Но к этому моменту уже
могли произойти два изменения: `.env` пересобран под 2.0 (прежний лежит рядом), и, если вы
запускали `make fix-users` в любом режиме кроме `scan`, изменены логины и адреса пользователей.
И то и другое откатывается только вручную — миграция тут ни при чём.

Если миграция упала, упавшая миграция откатывается целиком, но применённые до неё в этом же
прогоне остаются. Поэтому возвращаться на предыдущую версию нужно вместе с базой — и именно в
таком порядке:

1. **Вернитесь на прежнюю версию кода и погасите стек 2.x.** Это должно быть первым: пока
   сервисы 2.0 работают, базу не отобрать. `--remove-orphans` убирает и контейнеры сервисов,
   которых в 1.5.0 не было:

   ```bash
   git checkout v1.5.0
   VERSION=$(cat VERSION) docker compose down --remove-orphans
   ```

2. **Верните конфигурацию.** Нужен **самый старый** из `.env.bak-*`: его создал первый запуск
   `make upgrade`, и только он ещё в формате 1.x. Более свежие копии уже без переменных, без
   которых 1.5.0 не запустится:

   ```bash
   cp "$(ls -tr .env.bak-* | head -1)" .env
   rm -f backups/.upgrade-unfinished
   ```

   Второй командой снимается отметка о незавершённом обновлении: пока она на месте,
   `make run` и `make update` на чекауте 2.0 отказываются стартовать.

   Если обновление успело создать хранилище метрик 2.x, удалите его том: пароли
   запекаются в него при создании, а вы только что вернули `.env` без них — следующий
   `make upgrade` сгенерирует новые, и telegraf с Grafana молча не смогут подключиться.
   Том держит только метрики 2.x, которых у вас ещё нет; история InfluxDB не трогается:

   ```bash
   docker compose rm -sf timescale 2>/dev/null || true
   docker volume rm "$(basename "$PWD")_timescaleData" 2>/dev/null || true
   ```

3. **Восстановите базу** из дампа, снятого перед миграцией. Существующую базу нужно пересоздать,
   иначе восстановление наткнётся на уже существующие таблицы:

   ```bash
   export VERSION=$(cat VERSION)
   docker compose up -d postgres
   docker compose exec -T postgres dropdb -U <POSTGRES_USER> <POSTGRES_DB>
   docker compose exec -T postgres createdb -U <POSTGRES_USER> -O <POSTGRES_USER> <POSTGRES_DB>
   gunzip -c backups/pg-<дата>.sql.gz | docker compose exec -T postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB>
   ```

   `export VERSION` нужен каждой команде `docker compose` — без него compose печатает
   предупреждение "VERSION variable is not set" на каждый вызов.

4. **Запустите прежнюю версию:** `make run`.

История метрик InfluxDB копируется в `backups/influx-<дата>/` по возможности. Если обновление
напечатало предупреждение «the InfluxDB backup is EMPTY», копии нет — история осталась только в
docker-томе `influxData`, не удаляйте его.

## Инфраструктурные изменения

- **Grafana хранит своё состояние** (дашборды, пользователи, организации) во
  встроенной SQLite, а метрики читает из TimescaleDB отдельной read-only ролью —
  отдельная база под Grafana не нужна.
- **Авторизатор туннеля** читает публичный JWT-ключ бэкенда из примонтированного
  файла (`BACKEND_APP_PUBLIC_KEY_PATH`), а не из PEM-в-переменной-окружения.
- Redis `6-alpine` → `7.4.8-alpine`.

### Удалено
- Переменная `BACKEND_APP_PUBLIC_KEY` (PEM-в-env) у авторизатора туннеля.
- Сервис InfluxDB и переменные `INFLUXDB_USERNAME` / `INFLUXDB_PASSWORD` /
  `INFLUXDB_TOKEN`.
- Переменная `ADMIN_USERNAME` и генерируемая `EMAIL_URL` вместе с целями
