## 📖 Описание

Документация по настройке и развертыванию облака Wiren Board в On-Premise окружении.

### Минимальные системные требования:
- OS: Linux(Ubuntu 24)
- CPU: 2 Cores
- RAM: 6GB
- HDD: 20GB

### Рекомендуемые системные требования:

- OS: Linux(Ubuntu 24)
- CPU: 4 Cores
- RAM: 8GB
- HDD: 40GB

> Минимальной конфигурации хватает для нескольких десятков контроллеров: стек занимает около 4 ГБ,
> остальное уходит под кеш базы. Ближе к сотне контроллеров метрики заметно прибавляют в аппетите —
> закладывайте рекомендуемую конфигурацию и место на диске из расчёта срока хранения метрик
> (`METRICS_RETENTION_DAYS`, по умолчанию 30 дней).
>
> Параллелизм фоновых задач по умолчанию рассчитан на сотню контроллеров и настраивается —
> см. [Производительность фоновых задач](#производительность-фоновых-задач).

> ⚠️ Необходимо, чтобы процессор или гипервизор вашей ВМ поддерживал инструкцию `x86-64-v2`. При использовании виртуальной машины может потребоваться параметр `host-passthrough` (или `CPU=host`).

### Особенности версии On-Premise

Основные отличия локального облака от нашего [wirenboard.cloud](https://wirenboard.cloud) связаны с обеспечением безопасности инстанса и уменьшением нагрузки на сервер.

#### Регистрация пользователей и демодоступ

В On-Premise:
- новый пользователь не сможет зарегистрироваться без приглашения от владельца или админа организации;
- нет кнопки «Демо-аккаунт».

#### Метрики

Пока доступна только бесплатная версия на 100 контроллеров, которую можно использовать в личных и коммерческих целях. В этой версии включена обязательная отправка обезличенных метрик к нам на сервер, что именно отправляется смотрите в админ-панели, раздел «On_Premise» → «Metrics».

Если ваш инстанс не сможет достучаться до нашего сервера сбора метрик [on-premise-metrics.wirenboard.cloud](https://on-premise-metrics.wirenboard.cloud), облако будет работать, но вы не сможете добавлять контроллеры.

В будущем будут платные тарифы где можно отключить отправку метрик и добавить больше контроллеров.

## ⚙️ Предварительная настройка

Перед развертыванием приложения должны быть выполнены следующие шаги:

### 1. DNS-записи

Во всех примерах ниже `your-domain.com` означает **полный внешний hostname вашего облака**. Если облако будет доступно по `https://cloud.example.com`, то везде нужно указывать именно `cloud.example.com`, а не корневой домен `example.com`.

Должны быть настроены следующие DNS-записи типа A:

```text
your-domain.com
*.your-domain.com
*.ssh.your-domain.com
*.http.your-domain.com
*.apps.your-domain.com
```

Они покрывают все следующие поддомены необходимые для работы сервиса:

```text
metrics.your-domain.com
metrics-ingest.your-domain.com
tunnel.your-domain.com
app.your-domain.com
agent.your-domain.com
ssh.your-domain.com
http.your-domain.com
*.ssh.your-domain.com
*.http.your-domain.com
apps.your-domain.com
*.apps.your-domain.com
```

### 2. Порты

Для работы облака необходимо, чтобы у вас были открыты следующие порты:

- `443` - для облака
- `7107` - для туннелей
- `7501` - для доступа к дашборду туннелей (Опционально)

> ⚠️ Если у вас уже заняты какие-то из этих портов вы можете переопределить их в `.env` файле.

> Если `443` порт уже занят другим веб-сервером, см. [Использование с другим веб-сервером](#-использование-с-внешним-веб-сервером-nginxapachecaddytraefik)

> 🔒 Подробная сетевая схема, направления соединений и правила фаервола — [doc/SECURITY_NETWORK.md](./doc/SECURITY_NETWORK.md)


### 3. DNS-записи для почты

Должны быть настроены MX, SPF, DKIM и DMARC записи для корректной отправки email.
Это необходимо для отправки электронных писем с приглашением в организацию, сброса пароля и тд.

> Если email отключён (см. [Работа без email](#работа-без-email)), этот шаг можно пропустить.

### 4. Сертификаты TLS

Сертификат должен быть выдан доверенным CA:
- Let's Encrypt (DNS challenge)
- Коммерческие CA (Sectigo, DigiCert и др.)

> ❌ Самоподписанные сертификаты не поддерживаются.

Если у вас есть сертификат для этого домена, то проверьте его SAN (перечень поддоменов):

Сертификат должен быть выпущен для того же значения, которое указано в `ABSOLUTE_SERVER`, включая поддомен. Например, если облако работает на `cloud.example.com`, сертификат нужен для `cloud.example.com`, `*.cloud.example.com`, `*.http.cloud.example.com`, `*.ssh.cloud.example.com` и `*.apps.cloud.example.com`.

```bash
openssl x509 -in "path/to/your/certs/fullchain.pem" -noout -text | grep -A1 "Subject Alternative Name"
```

Сертификат должен включать:

```text
your-domain.com
*.your-domain.com
*.http.your-domain.com
*.ssh.your-domain.com
apps.your-domain.com
*.apps.your-domain.com
```

В противном случае вам придется получить новый.

> ⚠️ `make check-certs` проверяет этот список и не даёт запустить облако, если какого-то домена нет. В частности, сертификат без `*.apps.your-domain.com` не пройдёт проверку.

---

Разместите полученные `fullchain.pem` и `privkey.pem` в `./tls` или настройте переменную окружения `TLS_CERTS_PATH`.

#### Продление сертификата

Сертификаты Let's Encrypt живут 90 дней. Traefik читает файлы сертификата при старте и **не
перечитывает их сам**, поэтому после каждого продления контейнер нужно перезапустить — иначе
облако продолжит отдавать просроченный сертификат, хотя новый уже лежит на диске.

Перечитать сертификат достаточно одному Traefik, весь стек останавливать не нужно — для этого есть
`make reload-certs`. Если сертификат выпущен через certbot, добавьте её в его хук, и продление
останется полностью автоматическим:

```bash
sudo certbot renew --deploy-hook "cd /path/to/cloud-on-premise && make reload-certs"
```

Разовое продление руками:

```bash
sudo certbot renew
make reload-certs
```

> Команда сначала проверяет новый сертификат (`make check-certs`) и только потом перезапускает
> Traefik — если продление прошло неудачно, облако продолжит работать на старом сертификате.


Пример получения сертификата при помощи `Certbot`, см. [Пример ручной настройки Wildcard сертификатов](#-пример-ручной-настройки-wildcard-сертификатов)

### Развёртывание в локальной сети (без публичного доступа)

Облако может работать полностью внутри локальной сети, без публичного IP-адреса. Но сертификат всё равно должен быть валидным публичным (см. шаг 4): агент контроллера `wb-cloud-agent` строго проверяет TLS, и с самоподписанным сертификатом активационная ссылка получена не будет — даже если веб-интерфейс в браузере открывается.

> ⚠️ Цель `make run-no-cert-check` пропускает только локальную проверку файлов сертификата перед запуском. Она **не** отключает проверку TLS на контроллерах и не делает самоподписанный сертификат рабочим.

Рабочая схема:

1. Возьмите поддомен реального домена, которым вы владеете, например `cloud.example.com`.
2. Получите wildcard-сертификат через DNS-challenge — публичный доступ к серверу для этого не нужен, см. [Пример ручной настройки Wildcard сертификатов](#-пример-ручной-настройки-wildcard-сертификатов).
3. Во внутреннем DNS создайте A-записи, указывающие полный hostname облака и все поддомены (см. [1. DNS-записи](#1-dns-записи)) на локальный IP сервера.
4. Укажите `ABSOLUTE_SERVER=cloud.example.com`.

> 💡 Для `*.ssh.your-domain.com`, `*.http.your-domain.com` и `*.apps.your-domain.com` во внутреннем DNS нужны wildcard-записи. DNS бытовых роутеров их не поддерживает — используйте dnsmasq, Pi-hole, AdGuard Home или полноценный DNS-сервер.

Контроллеры должны резолвить тот же hostname через тот же внутренний DNS, что и остальные устройства сети.

### 5. Кастомный логотип и иконки

Этот шаг опционален.

Фронтенд и веб-консоль читают брендовые ассеты из локальной директории `branding/`, которая монтируется в контейнеры `frontend` и `webssh`.
Если не добавлять туда свои файлы, приложение продолжит работать с логотипом и иконками Wiren Board по умолчанию.

Чтобы заменить логотип и иконки, положите туда свои файлы с точными именами. Требования к файлам:

| Файл | Формат и размер | Где используется |
|---|---|---|
| `branding/logo.svg` | SVG, горизонтальный, ориентир 160×40 (отображается с шириной 160px, высота по пропорции) | логотип в шапке веб-интерфейса и веб-консоли |
| `branding/favicon.svg` | SVG, квадратный | иконка вкладки в современных браузерах |
| `branding/favicon.ico` | ICO, размеры 16–64 px | иконка вкладки в старых браузерах |
| `branding/favicon-192.png` | PNG, ровно 192×192 | иконка приложения (web manifest) |
| `branding/favicon-512.png` | PNG, ровно 512×512 | иконка приложения (web manifest) |
| `branding/apple-touch-icon.png` | PNG, 180×180 | иконка на домашнем экране iOS |

Размеры не проверяются автоматически: файл с неподходящими пропорциями будет отдан как есть и может отображаться некорректно.

Вы также можете заменять эти файлы частично.

Если проект уже запущен, после замены файлов перезапустите фронтенд и веб-консоль:

```shell
docker compose restart frontend webssh
```

Помимо ассетов можно переопределить название продукта, ссылки и цвет, которые веб-интерфейс и веб-консоль показывают пользователю. Для этого раскомментируйте и заполните переменные в `.env`:

```text
SERVICE_NAME       — название продукта: тексты интерфейса и заголовок вкладки (по умолчанию «Wiren Board Cloud»)
SERVICE_STATUS_URL — ссылка на страницу статуса ваших сервисов (не задана или пустая — ссылка на статус не показывается)
SERVICE_DOCS_URL   — ссылка на документацию (не задана — вики Wiren Board; пустая — ссылка не показывается)
PRIMARY_COLOR      — цвет основной кнопки в hex (например, #e2500a); если не задан, используется цвет по умолчанию
FOOTER_SITE_URL    — ссылка «сайт компании» в футере (не задана — wirenboard.com; пустая — ссылка не показывается)
FOOTER_SITE_LABEL_RU — подпись этой ссылки для русского языка (по умолчанию «Сайт компании Wiren Board»)
FOOTER_SITE_LABEL_EN — подпись этой ссылки для английского языка (по умолчанию «Wiren Board website»); если задана только одна из подписей, она используется для обоих языков
```

Если переменные не заданы, используются значения Wiren Board по умолчанию. После изменения `.env` перезапустите фронтенд и веб-консоль.

## 🚀 Развертывание приложения

> Для запуска вам понадобится Docker Compose v2 (проверьте: `docker compose version`).

### 1. Настройка переменных окружения

Создайте копию файла окружения и заполните его:

```bash
cp .env.example .env
nano .env
```

Каждая переменная описана комментарием в самом `.env.example` — дублировать их здесь мы не
стали, чтобы описание не разъезжалось с файлом. До первого запуска достаточно знать
следующее:

- `ABSOLUTE_SERVER` — полный внешний hostname облака: для `https://cloud.example.com` это
  `cloud.example.com`. От него строятся все поддомены, и он должен совпадать с сертификатом.
- `ADMIN_EMAIL` и `ADMIN_PASSWORD` — первый администратор облака. Email одновременно
  является логином.
- Переменные `EMAIL_*` можно не заполнять, если отправка писем отключена — см.
  [Работа без email](#работа-без-email).
- `METRICS_RETENTION_DAYS` — срок хранения метрик. Задаётся **до первого запуска**: потом его
  можно уменьшить, но не увеличить, иначе хранилище метрик придётся создавать заново.
- Секреты и пароли — `SECRET_KEY`, `TUNNEL_AUTH_TOKEN`, ключи JWT, `ABSOLUTE_SERVER_REGEX`,
  пароли хранилища метрик — руками писать не нужно: их создаёт `make generate-env`, который
  выполняется и при `make run`. В `.env.example` их нет, и до первого запуска
  `make check-env` сообщит об их отсутствии — это ожидаемо.

> ⚠️ Пароли хранилища метрик прописываются в него при создании. Менять их в `.env` после
> первого запуска бесполезно: пароли в самом хранилище останутся прежними, а связь с ним
> оборвётся.

> После любой правки `.env` перезапустите стек: `make restart`.


### 2. Автоматическая инициализация и запуск

Установите пакет `make`, если он ещё не установлен:

```bash
apt install make
```

Выполните команду, которая сгенерирует все необходимые секретные ключи и токены и запустит проект:

```bash
make run
```

✅ Поздравляем! Ваше облако готово к работе.

## ▶️ Использование

### Регистрация пользователей

В on-premise облаке регистрация сторонних пользователей отключена.
Доступ к системе изначально имеет только один пользователь с правами администратора,
чьи логин и пароль берутся из переменных окружения `ADMIN_EMAIL` и `ADMIN_PASSWORD` при запуске проекта.
Начиная с версии 2.0.0 логин — это email, поэтому администратор входит по значению `ADMIN_EMAIL`.

> ⚠️ Вы можете сменить пароль в любое время и создать другого администратора,
> но имейте в виду, что, если вы удалите пользователя,
> который указан в переменных окружения, он создастся снова при перезапуске проекта.

Первую организацию администратор создаёт вручную через [административную панель](#административная-панель).

Добавление новых пользователей возможно только через [административную панель](#административная-панель) или по приглашению на электронную почту.

После получения приглашения пользователь может перейти по ссылке в письме и зарегистрироваться.


### Административная панель

Административная панель (Django admin) доступна по адресу `https://app.your-domain.com/admin/`.
Для входа используйте email и пароль администратора из переменных окружения `ADMIN_EMAIL` и `ADMIN_PASSWORD`.

Через неё администратор создаёт первую организацию, приглашает пользователей, управляет ими и другими объектами системы.

> ⚠️ Административная панель даёт полный доступ к данным инстанса — не открывайте к ней доступ извне без необходимости.


### Настройка контроллера

Для настройки контроллера на работу с вашим on-premises облаком, необходимо выполнить следующие шаги:

#### 1. Добавить провайдера облака

Во всех командах ниже используйте тот же внешний hostname, что и в `ABSOLUTE_SERVER`. Если облако разворачивается на поддомене, подставляйте именно этот поддомен целиком.

##### В новых релизах начиная с wb-2507 и testing (агент > 1.5.14)

```bash
wb-cloud-agent use-on-premise https://your-domain.com
```

> После того как your-domain.com будет доступен в сети, команда `wb-cloud-agent` выведет активационную ссылку по которой можно будет связать контроллер с вашим облаком.

##### В старых релизах до wb-2504 включительно (агент <= 1.5.14)

Зайти в консоль самого контроллера и выполнить следующую команду:
```bash
wb-cloud-agent add-provider your-onpremise-name https://your-domain.com/ https://your-domain.com/api-agent/v1/
```
где:
- `your-onpremise-name` - название провайдера (можно задать любое)
- `https://your-domain.com/` - адрес облака
- `https://your-domain.com/api-agent/v1/` - адрес агента облака. Адрес всегда будет: `адрес облака` + `/api-agent/v1/`

> После того как your-domain.com будет доступен в сети, перейдите в web ui контроллера в раздел `Настройки -> Система` и перейдите по активационной ссылке с помощью которой можно связать контроллер с вашим облаком.
>
#### 2. Привязать контроллер к пользователю

Перейдите в веб-интерфейс контроллера, выберите:

`Настройки` -> `Система` -> `Подключение к облаку (your-onpremise-name)`

> Если вы не видите в настройках пункт `Система`, значит у вас нет прав администратора.
>
> Перейдите в `Настройки` -> `Права доступа` и выберите пункт `Администратор` -> `Я принимаю всю ответственность...` -> `Применить`
>
> После этого пункт `Система` появится в меню.

Перейдите по ссылке, авторизуйтесь в облаке и выберите организацию, куда хотите добавить контроллер.

Ваш контроллер успешно привязан к облаку.

> ⚠️ Отправка метрик с контроллера в On-Premise облако поддерживается только на версиях агента `wb-cloud-agent` до `1.6.14` включительно. На более новых версиях агента метрики контроллера в On-Premise облако отправляться не будут.

### Веб-сервисы контроллеров

Облако публикует веб-интерфейсы сервисов, работающих на контроллере
(например, Node-RED), через облачный туннель. Каждый сервис получает адрес вида
`<серийник>-<порт>.apps.your-domain.com`, доступ к нему — только через облачную
авторизацию. На один контроллер можно опубликовать до 20 сервисов.

Что требуется от оператора облака:

- wildcard DNS-запись `*.apps.your-domain.com` (см. [1. DNS-записи](#1-dns-записи));
- сертификат с SAN `apps.your-domain.com` и `*.apps.your-domain.com`
  (см. [4. Сертификаты TLS](#4-сертификаты-tls)). Wildcard выдаётся только через
  DNS-01 challenge (HTTP-01 wildcard не поддерживает) — это тот же механизм,
  которым получается остальной сертификат облака.

`*.apps.your-domain.com` входит в обязательный набор доменов сертификата:
без него `make check-certs` (а значит и `make run`) остановится с ошибкой.

### Геолокация сессий (GeoIP)

В списке активных сессий пользователя облако может показывать страну и город
по IP-адресу. Для этого раскомментируйте в `.env`:

```dotenv
GEOIP_ENABLED=True
```

При `make run` (точнее, на шаге `make generate-env`) база DB-IP «IP to City Lite»
(лицензия CC BY 4.0) скачивается автоматически в `./geoip`: ~62 МБ загрузки,
~124 МБ в распакованном виде.

DB-IP выпускает новую версию базы каждый месяц, а автоматическая загрузка забирает только
отсутствующую. Обновить её вручную: `make update-geoip` — старая база заменяется только после
полной загрузки, так что неудачное обновление ничего не ломает.

Если у сервера нет доступа в интернет, скрипт напечатает инструкцию: скачайте
базу «IP to City Lite» в формате MMDB с
[db-ip.com/db/download/ip-to-city-lite](https://db-ip.com/db/download/ip-to-city-lite)
на любой машине с интернетом, положите распакованный файл как
`./geoip/dbip-city-lite.mmdb` и выполните `make restart`.

Сама геолокация работает полностью офлайн: наружу облако запросов не делает.
DB-IP обновляет базу ежемесячно — обновление по желанию (просто замените файл).

Без базы всё работает, локация в списке сессий остаётся пустой. Приватные
адреса (LAN/VPN) не геолоцируются — это ожидаемое поведение.

### Производительность фоновых задач

Фоновые задачи облака разнесены по четырём очередям, у каждой свой обработчик и своя настройка
параллелизма.

| Переменная | По умолчанию | Что выполняет очередь | Когда поднимать |
|---|---|---|---|
| `WORKER_CONCURRENCY` | 4 | Основная очередь: обслуживание туннелей и соединений, отправка обезличенных метрик вендору, обслуживание организаций | Много контроллеров подключается и отключается одновременно |
| `METRICS_WORKER_CONCURRENCY` | 3 | Хранилище метрик: роли и политики хранения в TimescaleDB, применение лицензионных сроков, регулярная проверка отстающих настроек сбора | Растёт число контроллеров и организаций |
| `GRAFANA_WORKER_CONCURRENCY` | 3 | Grafana и настройка сбора: дашборды, пользователи, рассылка контроллерам конфигурации сбора метрик | Метрики от новых контроллеров появляются с задержкой, дашборды создаются медленно |
| `EMAIL_WORKER_CONCURRENCY` | 2 | Письма облака: приглашения, подтверждение почты, сброс пароля | Массовые рассылки приглашений |

> Письма оповещений по метрикам отправляет сама Grafana, эта очередь их не касается.

**Значения по умолчанию рассчитаны на сотню контроллеров** — потолок бесплатной версии.
Поднимать их для обычной инсталляции не нужно: раньше упрётесь в память и диск под метрики.

Каждая единица параллелизма — отдельный процесс, примерно **85 МБ**. Прибавка считается просто:
`+1` к любой переменной — ещё около 85 МБ.

| Профиль | Значения | Память под воркеры |
|---|---|---|
| Минимальный: несколько контроллеров, экономим память | 2 / 1 / 1 / 1 | ~0.5 ГБ |
| **По умолчанию: до 100 контроллеров** | **4 / 3 / 3 / 2** | **~1.3 ГБ** |
| Большая инсталляция: много организаций, массовые рассылки | 8 / 8 / 8 / 4 | ~2.5 ГБ |

Верхней границы нет — ограничение только память сервера.

**Как понять, что пора поднимать.** Признак нехватки — не медленный интерфейс, а задержка
результата: дашборд создался не сразу, метрики от нового контроллера появились не через минуту,
письмо ушло с опозданием. Проверить объективно можно длиной очереди — если она держится больше
нуля, задачи копятся:

```bash
docker compose exec redis redis-cli llen metrics_queue
```

Очереди: `default_queue`, `metrics_queue`, `grafana_queue`, `email_queue`. После правки `.env`
примените изменения: `make restart`.

> Оценки выведены из фактического расхода памяти на процесс; пропускная способность зависит от
> конкретной нагрузки, поэтому ориентируйтесь в первую очередь на длину очередей у себя.

### Работа без email

Если у вас нет SMTP-сервера, облако может работать без отправки email. Для этого задайте в `.env`:

```dotenv
EMAIL_ENABLED=False
```

При `EMAIL_ENABLED=False`:

- письма перестают отправляться — молча, без каких-либо ошибок;
- переменные `EMAIL_*` заполнять не нужно: `make run` и `make check-env` не требуют их;
- DNS-записи для почты (раздел [3. DNS-записи для почты](#3-dns-записи-для-почты)) настраивать не нужно;
- **приглашение пользователя в организацию** (в два шага, так как письмо не отправляется):
  1. во фронтенде владелец или администратор организации приглашает пользователя по email (в разделе участников организации);
  2. откройте [административную панель](#административная-панель) → раздел **Organizations** → нужная организация → блок **Organization invites** и скопируйте значение поля **link**. Передайте ссылку пользователю любым способом — по ней он зарегистрируется без подтверждения почты.

  > Создать приглашение прямо из административной панели нельзя — она показывает ссылку уже существующих приглашений. Само приглашение создаётся во фронтенде (шаг 1).
- **сброс пароля пользователю:** в [административной панели](#административная-панель) откройте раздел **Users**, отметьте пользователя галкой, в выпадающем списке **Действие** выберите **«Generate password reset link»** и нажмите «Выполнить». Ссылка появится в зелёном сообщении вверху страницы — скопируйте и передайте пользователю. Неактивные пользователи и пользователи без заданного пароля (например, вошедшие через соцсеть) пропускаются.

> ⚠️ Начиная с версии 2.0.0 переменная `EMAIL_ENABLED` обязательна: без явного `True`/`False` стек не стартует.

## 📦 Управление проектом через Makefile

Для работы с on-premise облаком используется набор команд Makefile.

## ⬆️ Обновление с 1.x до 2.0

Релиз **2.0** несовместим с 1.x, но **данные пользователей не удаляются** — они мигрируют на
месте. Главное изменение: **email становится логином** — он обязателен, уникален и должен
совпадать с именем учётной записи. Схема новой версии этого требует, но сама данные не
исправляет, поэтому базу нужно привести в порядок до миграции — это делает `make upgrade`.

Обновление выполняется одной командой:

```bash
git pull
make upgrade
```

Она проходит проверки при работающем облаке и ничего не меняет, пока все они не пройдены,
затем спрашивает подтверждение и только после него начинает простой.

> 📖 Условия миграции, разбор конфликтов учётных записей, ожидаемое время простоя и процедура
> отката — в [`RELEASE_NOTES_2.0.md`](migration/RELEASE_NOTES_2.0.md). Прочитайте его **до** запуска
> обновления: там же описано, что решить заранее (например, срок хранения метрик).

## 🔧 Пример ручной настройки Wildcard сертификатов

### Установка Certbot

```bash
sudo apt update && sudo apt install certbot -y
```

### Получение сертификата с wildcard-доменами

Укажите email к которому будет привязан сертификат и доменное имя:

Используйте полный hostname облака. Если облако будет доступно по `https://cloud.example.com`, то `DOMAIN_NAME=cloud.example.com`.

```bash
export EMAIL=admin@email.com
export DOMAIN_NAME=your-domain-name.com
```

Запустите Certbot выполнив команду:

```bash
sudo certbot certonly --manual --preferred-challenges dns \
  --agree-tos \
  --email $EMAIL \
  --key-type rsa \
  -d $DOMAIN_NAME \
  -d "*.$DOMAIN_NAME" \
  -d "*.ssh.$DOMAIN_NAME" \
  -d "*.http.$DOMAIN_NAME" \
  -d "apps.$DOMAIN_NAME" \
  -d "*.apps.$DOMAIN_NAME"
```

> Все шесть строк `-d` обязательны: без `*.apps.$DOMAIN_NAME` не пройдёт `make check-certs`.

И последовательно создайте записи на вашем DNS-сервере на основе того что выдаст Certbot:

### 🔹 Первая запись от Certbot

```
Type: TXT
Name: _acme-challenge.your-domain-name.com.
Value: some_token_1
```

Добавьте запись в ваш DNS-сервер.

Не закрывая окно терминала проверьте в другом окне создана ли запись:

```bash
dig TXT _acme-challenge.your-domain-name.com +short
```

Если запись создана, нажмите **Enter** (Continue) в первом окне.

### 🔹 Вторая запись (`http`) по аналогии с первой

```
Type: TXT
Name: _acme-challenge.http.your-domain-name.com.
Value: some_token_2
```

Проверьте:

```bash
dig TXT _acme-challenge.http.your-domain-name.com +short
```
Если запись создана, нажмите **Enter** (Continue).

### 🔹 Третья запись (`ssh`) по аналогии с предыдущими

```
Type: TXT
Name: _acme-challenge.ssh.your-domain-name.com.
Value: some_token_3
```

Проверьте:

```bash
dig TXT _acme-challenge.ssh.your-domain-name.com +short
```

Если запись создана, нажмите **Enter** (Continue).

### 🔹 Четвёртая запись (`apps`) по аналогии с предыдущими

```
Type: TXT
Name: _acme-challenge.apps.your-domain-name.com.
Value: some_token_4
```

> Для `apps.$DOMAIN_NAME` и `*.apps.$DOMAIN_NAME` Certbot попросит **две** TXT-записи с одинаковым именем — добавьте обе.

Проверьте:

```bash
dig TXT _acme-challenge.apps.your-domain-name.com +short
```

Если записи созданы, нажмите **Enter** (Continue).

### ✅ Результат

Certbot сохранит сертификат по пути:

```
/etc/letsencrypt/live/your-domain.com/fullchain.pem
/etc/letsencrypt/live/your-domain.com/privkey.pem
```

### Проверка RSA-ключа

```bash
openssl rsa -in /etc/letsencrypt/live/$DOMAIN_NAME/privkey.pem -check -noout
```

Должно быть:

```
RSA key ok
```

## 🛡 Использование с внешним веб-сервером (Nginx/Apache/Caddy/Traefik)

Если на сервере уже установлен внешний веб-сервер (например, Nginx, Apache), который использует 443 порт, настройте on-premise облако следующим образом:

> ⚠️ Во всех примерах ниже `your-domain.com` — это **полный hostname облака**,
> то же значение, что в `ABSOLUTE_SERVER`. Если облако развёрнуто на поддомене
> (например, `cloud.example.com`), подставляйте поддомен целиком: в regex это
> даст `cloud\.example\.com` (точки экранируются как `\.`), а wildcard-формы —
> `[^.]+\.cloud\.example\.com` и т.д. SNI, не совпавший с regex, не будет
> проброшен в Traefik облака — браузер покажет ошибку сертификата или обрыв
> соединения.

### 1. В `.env` задайте переменную:
    ```
    TRAEFIK_EXTERNAL_PORT=127.0.0.1:8443
    ```
    По умолчанию Traefik слушает 443 порт на сервере. Если переменная `TRAEFIK_EXTERNAL_PORT` указана как в примере, Traefik будет слушать только на локальном порту 8443, не занимая 443 порт на сервере.

### 2. Настройте проксирование во внешнем веб-сервере.

> ⚠️ **Поддомен `agent.*` использует взаимную аутентификацию по TLS (mTLS): контроллер предъявляет аппаратный клиентский сертификат, который проверяет Traefik.**
> Стандартное L7-проксирование (когда nginx терминирует TLS) **не передаёт клиентский сертификат дальше**, что ломает аутентификацию контроллеров.
> Поэтому для всего on-premise трафика необходимо использовать **L4 TCP passthrough** через модуль `stream` — nginx пробрасывает TCP-соединение «как есть», а Traefik сам завершает TLS и выполняет проверку mTLS.

#### Кейс A: nginx используется только для on-premise

Удалите существующий `server { listen 443 ssl; ... }` блок для on-premise доменов и добавьте блок `stream` на верхнем уровне конфига:

```nginx
# /etc/nginx/nginx.conf — на верхнем уровне, не внутри http {}
stream {
    server {
        listen 443;
        ssl_preread on;
        proxy_pass 127.0.0.1:8443;
    }
}
```

Все HTTPS-запросы на порту 443 будут прозрачно проброшены в Traefik на порту 8443.

#### Кейс B: nginx также обслуживает другие сайты на порту 443

Используйте `ssl_preread` с `map` для маршрутизации по SNI: on-premise домены идут в Traefik, остальные — на отдельный HTTP-листенер nginx.

```nginx
# /etc/nginx/nginx.conf — на верхнем уровне, не внутри http {}
stream {
    map $ssl_preread_server_name $upstream {
        ~^(.+\.)?your-domain\.com$  127.0.0.1:8443;  # on-premise → Traefik
        default              127.0.0.1:444;   # остальные сайты → nginx http
    }

    server {
        listen 443;
        ssl_preread on;
        proxy_pass $upstream;
    }
}

# В блоке http {} обычные сайты переводим на порт 444
server {
    listen 444 ssl;
    server_name your-domain.com;

    ssl_certificate     /etc/letsencrypt/live/your-domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;

    location / {
        # ваши обычные настройки
    }
}
```

> Убедитесь, что порт 8443 (или другой указанный в `TRAEFIK_EXTERNAL_PORT`) не открыт наружу. Достаточно проброса только на 127.0.0.1, как указано выше.

#### Кейс C: внешний Traefik (TCP passthrough)

Если перед облаком уже стоит свой Traefik (например, краевой reverse-proxy в DMZ), маршрутизируйте трафик по SNI на уровне L4 и **обязательно с `passthrough`** — по той же причине, что и для nginx выше: внешний Traefik не должен терминировать TLS, иначе сломается mTLS-аутентификация контроллеров на `agent.*`.

В отличие от nginx-примеров, через внешний прокси нужно пробросить **все три точки входа** облака, а не только 443:

- `443` — веб-интерфейс, API и агентский endpoint;
- `7107` — туннели;
- `7501` — дашборд туннелей (опционально).

**1. Статический конфиг внешнего Traefik.** Объявите три entryPoint — иначе Traefik отбросит роутеры `tunnel`/`tunnelui` (в логе будет `entryPoint ... doesn't exist`):

```toml
[entryPoints.websecure]
  address = ":443"
[entryPoints.tunnel]
  address = ":7107"
[entryPoints.tunnelui]
  address = ":7501"
```

Убедитесь, что эти порты опубликованы (проброшены наружу) на самом внешнем Traefik.

**2. Динамический конфиг** (file-провайдер) — маршрутизация по SNI на хост облака:

```yaml
tcp:
  routers:
    wbc-https:
      entryPoints: ["websecure"]
      rule: "HostSNIRegexp(`^(your-domain\\.com|[^.]+\\.your-domain\\.com|[^.]+\\.(http|ssh|apps)\\.your-domain\\.com)$`)"
      tls:
        passthrough: true          # ⚠️ не терминировать TLS — нужно для mTLS контроллеров
      service: wbc-https

    # Туннели контроллеров
    wbc-tunnel:
      entryPoints: ["tunnel"]
      rule: "HostSNI(`*`)"
      service: wbc-tunnel

    # UI туннелей
    wbc-tunnel-ui:
      entryPoints: ["tunnelui"]
      rule: "HostSNI(`*`)"
      service: wbc-tunnel-ui

  services:
    wbc-https:
      loadBalancer:
        servers:
          - address: "<cloud-host>:443"
    wbc-tunnel:
      loadBalancer:
        servers:
          - address: "<cloud-host>:7107"
    wbc-tunnel-ui:
      loadBalancer:
        servers:
          - address: "<cloud-host>:7501"
```

где `<cloud-host>` — адрес сервера с on-premise облаком, а `your-domain.com` — полный hostname облака (как в `ABSOLUTE_SERVER`).

> ⚠️ Правило `HostSNIRegexp` требует Traefik **v3**: на Traefik v2 у TCP-роутеров нет `HostSNIRegexp` — конфиг там не заработает.

> ⚠️ Обратите внимание на кавычки в YAML: в **двойных** кавычках бэкслеши
> удваиваются (`your-domain\\.com`, как в примере выше), в **одинарных** — пишутся
> одиночными (`your-domain\.com`). Одиночный `\.` внутри двойных кавычек даст
> ошибку `yaml: found unknown escape character`, file-провайдер отбросит весь файл,
> и Traefik начнёт отдавать свой default-сертификат вместо passthrough.

> Регулярка матчит те же хосты, что покрывает wildcard-сертификат облака (см. раздел «Сертификаты TLS»): сам `your-domain.com`, любой поддомен первого уровня (`app.`, `agent.`, `ssh.`, `http.` и т.д.), per-controller `<id>.http.`/`<id>.ssh.` и `<серийник>-<порт>.apps.`. Подставьте свой домен из `ABSOLUTE_SERVER` вместо `your-domain.com`.

> Если через внешний прокси нужно экспонировать только контроллерный трафик, оставив веб-интерфейс облака недоступным извне, сузьте регулярку до `agent.your-domain.com` и per-controller хостов `<id>.http.`/`<id>.ssh.`.

> Если внешний Traefik стоит на том же сервере, что и облако, дополнительно уведите внутренний Traefik облака на локальный порт через `TRAEFIK_EXTERNAL_PORT` (см. начало раздела) и проксируйте на `127.0.0.1`, чтобы порты не конфликтовали.
