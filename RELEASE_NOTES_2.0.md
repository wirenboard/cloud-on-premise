# On-Premise 2.0 — что нового

Мажорный релиз: большой синк с актуальным облаком + несовместимые изменения в
учётных записях. Данные пользователей **не удаляются** — они мигрируют на месте.

Краткий список изменений — в [`CHANGELOG.md`](CHANGELOG.md). Здесь — подробности и
порядок обновления. Релиз включает всё из 1.3.0–1.5.0 (отключаемый email,
ребрендинг, security-фикс туннельного авторизатора).

---

## Новые возможности

### Дашборды Grafana по организациям
Новый сервис `clients-grafana` (Grafana 12.2.2) — отдельные пользовательские
дашборды в разрезе организаций. Своё состояние (дашборды, пользователи, организации)
Grafana хранит во встроенной SQLite (`/var/lib/grafana`, том `clientsGrafanaData`),
а метрики читает из TimescaleDB как datasource.

### Метрики на TimescaleDB
Хранилище метрик переведено с InfluxDB на **TimescaleDB**. Приём метрик от
контроллеров теперь выполняет сервис **Telegraf** (HTTPS + mTLS, ограничение частоты
через Traefik). Для одноузловой поставки запускается один инстанс TimescaleDB (без
upstream-HA: Patroni/etcd/HAProxy не используются).

> **Важно:** история метрик за прошлый период в новые графики **не переносится**.
> Существующая база InfluxDB при обновлении сохраняется в бэкап, новые метрики
> копятся в TimescaleDB с нуля. Графики за период до обновления будут пустыми;
> исторические данные при необходимости можно поднять из бэкапа отдельно.

### Ежедневные бэкапы PostgreSQL в S3
Сервис `postgres-backup` — регулярный логический бэкап основной базы PostgreSQL в
bundled MinIO (S3-совместимое хранилище).

### Вебхуки FRP-туннелей
Отдельный инстанс бэкенда `tunnel-webhooks-backend` для обработки вебхуков
FRP-туннелей (изолирован от основного трафика приложения).

### Разделение фоновых задач по очередям
Воркеры Celery разнесены по очередям: `default`, `metrics`, `grafana`, `email` —
тяжёлые/медленные задачи больше не блокируют друг друга.

### Веб-сервисы контроллеров через туннели (опционально)
Веб-интерфейсы сервисов контроллера (например, Node-RED) публикуются на поддоменах
`<серийник>-<порт>.apps.<домен>` — до 20 сервисов на контроллер, доступ только через
облачную авторизацию. Требует wildcard DNS-запись и сертификат для
`*.apps.<домен>` (см. README). Без этой настройки облако полностью работает,
но ссылки сервисов не открываются.

### Быстрые туннели
Пул прогретых каналов до контроллера (`TUNNEL_POOL_COUNT`, по умолчанию 5) —
страницы за туннелем открываются заметно быстрее.

### Геолокация сессий (опционально)
Страна/город в списке активных сессий — по локальной базе DB-IP, без запросов
наружу (см. README, раздел GeoIP).

## Несовместимые изменения

### Вход по email
Email стал логином: **обязателен и уникален** (без учёта регистра). Учётные записи
без email или с логином, не совпадающим с email, больше не допускаются.

Несовместимость на уровне БД вводит upstream-миграция `users/0013` (делает email
уникальным логином). Она идёт **без переноса данных**, поэтому заполненную базу 1.x
нужно привести в порядок **до** миграции — этим занимается `make upgrade` (см. ниже),
данные при этом **не теряются**.

### Адрес регистрации
Старый эндпоинт `/users-sign-up/` удалён (в upstream заменён на
`/users/registrations/`). Встроенный фронтенд обновляется синхронно — страница
регистрации для пользователя продолжает работать.

### `EMAIL_ENABLED` стала обязательной
Стек не стартует без явного `EMAIL_ENABLED=True` или `EMAIL_ENABLED=False` в
`.env`. В 1.x незаданная переменная молча включала email — теперь выбор нужно
сделать явно (иначе письма могли тихо теряться при недонастроенной почте).

## Как обновиться (1.x → 2.0)

Одной командой:

```bash
make upgrade
```

Порядок, который она выполняет:

1. **Обязательный бэкап** (`pg_dump` + `influxd backup`) — до любых изменений в БД.
2. **Проверка таблицы пользователей** на конфликты 2.0 (пустой/NULL email,
   `username != email`, дубликаты email).
3. **Гейт:** если конфликты остались — остановка с выводом команды исправления,
   миграция **не запускается**.
4. `migrate` на образе 2.0.
5. Поднятие стека 2.0.

### Ремонт учётных записей

Если на шаге 2 нашлись конфликты — `make fix-users` (обёртка над
`migration/migration_doctor.py`):

- **Безопасные случаи** исправляются автоматически: приведение email к нижнему
  регистру; устранение различий только в регистре/пробелах; email администратора из
  `ADMIN_EMAIL`.
- **Остальное** решается через интерактивный мастер (`MODE=resolve`) либо через
  безголовый режим: `MODE=dump` → правка `conflicts.yaml` → `MODE=apply`.
- Оба режима валидируются (корректный email, отсутствие новой коллизии).
  Идемпотентно — можно перезапускать до 0 конфликтов.

Отдельный бэкап в любой момент: `make backup` (PostgreSQL + InfluxDB в `./backups`).

## Инфраструктурные изменения

- **Бэкенд подключается к PostgreSQL напрямую** (`postgres:5432`). Пул соединений
  pgcat убран как избыточный для одноузловой поставки (пулинг/шардинг/разведение
  чтений — задачи upstream-HA, которых здесь нет).
- **Внутренняя БД Grafana** — встроенный SQLite вместо внешнего PostgreSQL.
  Переменные источника данных теперь `GRAFANA_TIMESCALE_USER` /
  `GRAFANA_TIMESCALE_PASSWORD`.
- **Авторизатор туннеля** читает публичный JWT-ключ бэкенда из примонтированного
  файла (`BACKEND_APP_PUBLIC_KEY_PATH`), а не из PEM-в-переменной-окружения.
- Redis `6-alpine` → `7.4.8-alpine`.

### Удалено
- Сервис pgcat и его конфигурация (`pgcat/pgcat.toml`).
- Внешняя БД состояния Grafana: `postgres/init-grafana-db.sh`, переменные
  `GRAFANA_DB_NAME` / `GRAFANA_DB_USER` / `GRAFANA_DB_PASSWORD`.
- Переменная `BACKEND_APP_PUBLIC_KEY` (PEM-в-env) у авторизатора туннеля.
- Сервис InfluxDB и переменные `INFLUXDB_USERNAME` / `INFLUXDB_PASSWORD` /
  `INFLUXDB_TOKEN`.
